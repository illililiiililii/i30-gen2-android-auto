# i30 GD13MY Android Auto — 성공 가능성 평가

작성일 2026-11-24 · 대상: DHU 2.1 신원 적용 후 오류 07 해소 가능성

> **이 문서의 숫자는 측정값이 아니라 조건부 주관 추정이다.** 근거는 저장소의 실측 로그와 공개 자료이며, 계산식으로 도출한 값이 아니다. 전제가 바뀌면 6절 규칙으로 갱신한다.

## 0. 전제

| 항목 | 값 |
|---|---|
| 폰 | 저장소에서 시험한 삼성 테스트폰 (Android 15, AA `18.0.664264-release`) |
| 적용 신원 | DHU 2.1 leaf + 개인키 (`iscle/android-auto-certificates`) |
| 신뢰 앵커 | GAL 루트 (`O=Google Automotive Link`) |
| 경로 | USB AOA (TCP 5277 보조) |
| 구현 | 저장소의 `src/ce/ce_aa_tls.c` (BearSSL 0.6) |

---

## 1. 결론

| 단계 | 성공 확률 | 판정 기준 |
|---|---|---|
| **① 폰이 DHU 신원 수락 → 오류 07 소멸** | **85~90%** | `unknown CA`(alert 48)가 사라지고 `AUTH_COMPLETE` 도달 |
| ② TLS 이후 서비스 탐색 | 75~85% | `encrypted service discovery request received` |
| ③ 실폰 화면 투사(영상+터치) | 55~70% | 800×480 프레임 + 탭 반응 |
| ④ 30분 무중단 실사용 | 30~50% | 30분 세션 유지, 분리/재연결 정상 |

한 줄 요약: **"07이 사라지는가"는 85~90%, "차에서 쓸 수 있는가"는 30~50%.** 이 둘은 다른 문제다.

---

## 2. ①을 85~90%로 보는 근거

| # | 근거 | 출처 |
|---|---|---|
| 1 | **같은 폰에서 DHU 신원이 이미 10회 연속 통과했다.** AA 1.7, TLS 1.2, `0xC02F`, 인증서 검증 성공, 800×480 영상 | `docs/USB_CONNECTION_TEST.md` (DHU 반복 10회) |
| 2 | **TLS 계층은 상대가 진짜 DHU 프로그램인지 구분하지 않는다.** 검증 대상은 인증서 체인이고, DHU leaf는 GAL 루트가 직접 서명(체인 길이 1) | `docs/certificates.md` (AARE) + DER 디코드 |
| 3 | **이식 대상 코드의 TLS 기계장치는 이미 검증됐다.** 시험 CA로 상호 TLS → `AUTH_COMPLETE` → 암호화 탐색 → 정상 종료 | `docs/CE_PORTING_STATUS.md` |
| 4 | **DHU 신원은 ADB/TCP 5277에서도 통한다.** USB 액세서리 문자열 같은 하드웨어 지문에 의존하지 않는다 | `docs/USB_CONNECTION_TEST.md`, DHU 문서 |

즉 "이 폰이 이 신원을 받아들인다"는 사실이 이미 실측으로 존재한다. 남은 것은 **같은 신원을 다른 프로그램이 제시하는 것**뿐이다.

---

## 3. 잔여 리스크 (실패 시 유력 원인 순)

| 순위 | 리스크 | 대략 비중 | 검출 방법 | 대응 |
|---|---|---|---|---|
| 1 | 폰이 DHU 신원을 **정책으로 제한** | 5~8% | `unknown CA`가 그대로 유지 | 구글 앱 경로 종료 → AARE/동글 |
| 2 | AOA 액세서리 문자열 차이로 **모드 분기** | 3~5% | TLS 통과 후 세션 즉시 종료 | 액세서리 문자열을 DHU와 동일하게 |
| 3 | CE 구현 실수(체인 순서, `.der` 잔재, 매니페스트) | 3~5% | `BR_ERR_X509_NOT_TRUSTED`, 로드 실패 | **통제 가능** — 제거 대상 |
| 4 | 게스트 시계 오차 | 2~3% | `rejected at guest UTC` | 호스트 UTC 동기화 |
| 5 | BearSSL suite/확장 미협상 | 1~2% | `cipher suite rejected` | suite 목록 확인 |

1~2순위는 **우리가 통제할 수 없는 외부 요인**이고, 3~5순위는 **재시도로 제거 가능한 내부 요인**이다. 그래서 "실패"가 나와도 대부분은 고칠 수 있는 실패다.

---

## 4. 확률을 올리는 가장 값싼 선행 시험

**CE를 건드리기 전에 PC 수신기로 인증서만 시험한다.** 1시간 내 ①의 답이 나온다.

```powershell
# 저장소 PC 수신기: --cert/--key(헤드유닛 신원), --ca/--peer-name/--peer-sha256(폰 검증)
python -m i30_receiver --usb `
  --cert dhu-cert.pem --key dhu-key.pem `
  --ca gal-root.pem --peer-name <폰 cert 이름> --peer-sha256 <지문>
```

| PC 결과 | 해석 | ① 확률 재평가 |
|---|---|---|
| TLS 완료 + `AUTH_COMPLETE(0)` | 인증서 게이트는 열린다 | **95% 이상** — CE 작업만 남음 |
| `unknown CA` (alert 48) | 폰이 DHU 신원 거부 | **5% 이하** — AARE/동글로 전환 |
| 스위트/시계/핀 오류 | 내 설정 문제 | 확률 불변, 수정 후 재시도 |

이 시험의 가치: **인증서 문제와 CE/MUSB 문제를 분리**한다. PC에서 되고 CE에서 안 되면 원인은 100% CE 쪽이며, 그건 고칠 수 있는 문제다.

---

## 5. ②③④가 낮은 이유 (인증서와 무관한 난이도)

| 단계 | 감소 요인 | 근거 |
|---|---|---|
| ② 서비스 탐색 | 서비스 광고·채널 라우팅 미완 | `ce_aa_tls.c`는 현재 미디어 채널 미등록 |
| ③ 화면 투사 | 포그라운드 권한(`I30.GD13MY.VideoSurface.1`), H.264 디코딩, 순정 창 클리핑 | `docs/CE_NATIVE_DISPLAY_INTEGRATION.md` |
| ④ 무중단 | USB Attach 8초 한도, 순정 `usbd.dll`이 분리 통지 전 파이프를 닫음, MUSB 0바이트 DMA 후 출력 중단 이력 | `docs/CE_PORTING_STATUS.md` |

즉 ①을 뚫어도 "화면이 나오는 것"과 "차에서 쓸 수 있는 것"은 별도 관문이 남는다.

## 6. 확률 갱신 규칙 (사전 정의)

| 관측 | ① 갱신 | 이유 |
|---|---|---|
| PC 수신기에서 DHU 신원으로 TLS 완료 | 85~90% → **95%** | 폰 정책 리스크 소거 |
| PC 수신기에서 `unknown CA` | 85~90% → **5%** | 정책 경계 확인 |
| CE에서 DHU 신원으로 TLS 완료 | → **99%(사실상 확정)** | 실측 |
| CE에서 `unknown CA`인데 PC에서는 성공 | ① 유지 | CE 구현 문제로 재분류 |
| 2026년 이후 Play Services 대형 업데이트 | **재평가 필요** | 2025년 `25.34.34` 선례 |

## 7. 비용·시간 추정

| 작업 | 예상 |
|---|---|
| PC 선행 시험(인증서만) | 1시간 |
| CE 이미지에 인증 자료 주입 + 매니페스트 | 1~2시간 |
| 실폰 USB 시험 1회 | 30분 (부팅 수 분 포함) |
| ② 서비스 탐색까지 | 1~2일 |
| ③ 화면 투사까지 | 1~2주 (영상·포그라운드 이슈에 따라 변동) |
| ④ 무중단 | 2주 이상 |

**1시간 투자로 85% vs 5%가 갈린다.** 순서를 지키는 것이 가장 중요하다.

---

## 8. 한계

- 이 추정은 **단일 폰·단일 저장소 상태** 기준이다. 다른 폰, 다른 AA 버전에서는 달라진다.
- ①은 "07이 사라진다"는 뜻이며, **합법성·약관 문제를 해결하지 않는다.** DHU 신원은 단일 공유 테스트 신원이고, 개인 검증 범위를 넘는 사용은 별도 판단이 필요하다.
- 확률은 확률일 뿐이다. **실패해도 `unknown CA` 유무로 원인이 즉시 갈리도록** 로그를 남기는 것이 이 추정보다 중요하다.
