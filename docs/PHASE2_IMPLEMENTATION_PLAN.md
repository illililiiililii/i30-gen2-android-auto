# Phase 2 · PC MVP와 실물 적용 기준

**PC에서 공식 DHU의 실폰 USB·TLS·영상·터치를 확인했다.** 자체 수신기의 실폰 검증은 AOA 및 Android Auto 1.7 응답까지 진행했다. 실제 영상·입력의 자체 수신기 검증은 아래 기준을 적용한다. CE용 바이너리를 OEM 시스템에서 시험하기 전에는 실물 식별, 허용되는 실행·복구 절차, USB bulk 전송, 영상 성능을 각각 확인한다. [현재 실폰 시험 결과](USB_CONNECTION_TEST.md)

| 순서 | PC MVP 범위 | 검증 기준 |
|---|---|---|
| 1. 기준 환경 | 지원 Android 스마트폰, 데이터 USB 케이블, Google DHU 2.x. DHU에서 공식 AOA 연결이 성립하는지 확인한다. | 폰/OS·AA 앱·DHU 버전, USB 장치 열거, 정상 화면이 표시되기까지의 시간을 기록한다. 동일 조건에서 10회 반복한다. [Google DHU](https://developer.android.com/training/cars/testing/dhu) |
| 2. 협상과 세션 | 테스트 폰과 PC 수신기에서 링크 전환, 버전 요청/응답, 보안 협상, 서비스 탐색과 영상 채널을 기록한다. | 10회 중 10회 연결하며 각 단계의 성공/실패를 분리해 기록한다. 정상 종료와 케이블 분리 후 새 세션을 검증한다. |
| 3. 영상 수신 | 뷰어에 연결할 동영상 수신 처리와 디코드 계층을 나눈다. 키프레임 이후 테스트 패턴 또는 테스트 폰의 정지 화면 및 지도 스크롤을 실제로 표시한다. | 선택된 크기와 프로파일을 로그로 남긴다. 협상된 480p 계열 30 fps부터 시작해 30분간 표시하고 프레임 누락·지연·피크 메모리·CPU를 기록한다. |
| 4. 기본 터치 | PC 뷰어에서 누름/이동/뗌을 화면 영역 좌표로 변환해 입력 서비스로 보낸다. | 가운데와 모서리 5점 탭, 드래그 및 분리 중 입력 해제를 검증한다. 레터박스 영역 입력은 배제하고 p95 실제 반응 시간 150 ms 이하를 초기 목표로 둔다. |
| 5. 장애·종료 | 전송 끊김, 연결 재시도, 버퍼 정리, 화면 닫기 및 재시작을 검증한다. | 10회 반복 연결 후 FD/핸들 및 메모리가 누적되지 않으며 연결 해제 후 다음 세션이 정상 동작한다. |

PC에서는 `Transport`(AOA/USB) → `ProjectionSession`(버전·서비스·채널) → `VideoSink`(디코드/표시)와 `InputSource`(이벤트)를 교체 가능한 경계로 둔다. `tools/projection_frames.py`를 초기 프레임 레이아웃 및 기록 확인 도구로 쓴다. `--frames`는 한 방향의 프레임 바이트만 읽는다. PCAP 헤더나 TLS 암호문을 복호화하지 않으며 조각을 재조립하지 않는다. 검증 시 인증 또는 연결 정책을 변경하지 않는다.

### 현재 완료 조건 판정

공식 DHU는 삼성 테스트폰에서 AOA와 인증이 있는 TLS 1.2, 화면 출력, 앱 런처 탭을 확인했다. 프로젝트 수신기는 실제 USB의 AOA·bulk 및 버전 응답, 모의 TLS의 서비스 탐색·채널·종료·재연결, 영상 미리보기와 5점 탭을 확인했다. [실폰 및 모의 시험 기록](USB_CONNECTION_TEST.md) · [PC 구축과 통합 시험](PHASE2_ARCHITECTURE.md)

업데이트한 서브폰에서도 공식 DHU의 TLS 1.2 인증서 검증과 800×480 화면 표시, 프로젝트 수신기의 AOA·bulk·Android Auto 1.7 응답까지 확인했다. 서브폰의 터치 반응은 판정 보류다. [장치별 실폰 검증 수준](USB_CONNECTION_TEST.md#실폰-검증-수준)

프로젝트 수신기의 실폰 TLS에는 폰 인증서를 검증할 신뢰 자료와 예상 인증서 이름 또는 지문이 필요하다. 폰이 클라이언트 인증을 요구하는 환경에서는 폰이 신뢰하는 테스트 수신기 인증서와 키도 필요하다. 실폰 연속 30분 화면 표시·프레임 지연, 화면 좌표 드래그·입력 해제와 순정 CE 실행은 미검증이다. [인증 자료와 실폰 통과 기준](USB_CONNECTION_TEST.md#인증-자료와-실폰-통과-기준) · [Phase 3 검증 계획](PHASE3_IMPLEMENTATION_PLAN.md)

### 순정 CE 적용 전 벤치 기준

1. 라벨/순정 SW 정보를 확보해 GD13MY 패키지와 매칭한다. 분리된 기기, OEM 하네스, 전류 제한 전원으로 정상 부팅 및 복구 절차를 확인한다.
2. 공급업체가 허용하는 경로에서 ARM/Thumb CE ABI의 작은 테스트 프로그램을 실행할 수 있는지 확인한다. USB 클라이언트 등록, enumeration, VBUS 및 bulk IN/OUT이 가능해야 한다. 같은 폰의 PC 세션 트래픽 p95를 기준으로 목표 처리량을 계산한다.
3. 구동 중 가용 RAM을 비교한 뒤 로컬 H.264 테스트 스트림으로 디코드·화면을 먼저 검증한다. 30분간 목표 영상이 표시되고 USB/영상 버퍼가 시간에 따라 증가하지 않아야 한다. OEM 유휴, 내비 활성, 카메라 전환 각각의 CPU와 최소 여유 RAM을 기록한다.
4. 후방 영상 우선권을 테스트한다. 순정 기준 30회와 동일한 시나리오를 비교해 후진 이벤트 누락이 0이어야 하며 화면 전환 지연이 순정 기준을 벗어나지 않아야 한다. 케이블 제거·수신기 장애 시에도 순정 UI, 카메라와 음량이 회복돼야 한다.
5. 영상과 터치가 안정화되면 음악·안내·마이크를 붙이고, 이후 OEM 버튼/통화 및 UI 전환 순으로 확장한다. 오디오 권한·덕킹·장치 반환 및 후방카메라 전환은 각 기능 추가 때 재검증한다.

지원되는 실행 경로를 찾지 못하거나, USB/DSP/카메라 중 하나라도 벤치 기준을 충족하지 못하면 순정 기기 구현은 보류한다. PC 검증 결과와 소스 수준의 설계 비교는 이 결정과 독립적으로 계속 축적한다.
