# GD13MY .061 DSP 이미지 및 H.264 판정

**판정은 C, 실제 디코딩 지원 판별 불가다.** 탑재 이미지에 H.264 디블록 코드를 확인했다. ARM 드라이버가 읽는 DSP 기능 비트, 그 비트를 생성하는 DSP 핸들러, 타입 6에서 실제 디코더로 이어지는 호출을 확인해야 한다. Baseline 800×480 초기화 및 30 FPS는 실측 전이다.

## 실행 이미지의 직접 근거

| 위치 | 확인한 동작 |
|---|---|
| ROM `dsp_bridge.dll`, SHA-256 `4e70275cd88034a63710cf863b663fb29d863811bf717b35a9bd2e70b9f665ae` | PE .text에 DSP 소스 데이터가 들어 있다. ARM 초기화가 사용하는 `0x10254410` 테이블에는 목적 주소, 바이트 수, PE 소스 VA 순의 항목 50개가 있다. 총 2,437,588바이트이며 0으로 끝난다. |
| `0x102557b8–0x102557d0` → `0x1025625c` → `0x10257730` | 순정 시작 시 이미지 테이블을 InitShuttle 경로에 전달한다. `0x10257530`부터 각 항목을 쓰고 `0x10257194`가 실제 복사를 호출한다. `0x102577f4–0x102577f8`부터 시작과 alive 확인을 수행한다. |
| 첫 항목 PE `0x10001238`, 로드 `0x83c00000`, 길이 `0x200` | C64x little-endian 명령에서 `0x83f21ac0`을 조합해 분기한다. 해당 주소도 테이블의 44번 항목(0부터 시작)에 포함되며 인터럽트·스택 초기화 명령을 확인했다. |
| DSP 코드 `0x83d99264–0x83d99298` | ARM 시작 경로에도 있는 handshake 상수 `0xabcd5678`과 `0x5a5a7c7c`를 명령으로 각각 조합한다. |
| DSP 데이터 `0x83ce38b8/0x83ce38f0`, 코드 `0x83e22a1c–0x83e22a50` | 표준 H.264 alpha/beta 디블록 표가 h264bsd의 각 52바이트 배열과 일치한다. DSP 코드가 두 포인터 값을 직접 조합한다. payload에 H.264 처리 코드가 있다는 근거다. 인코더·디코더 양쪽에서 쓰는 디블록이므로 이 근거로 디코더 등록, 프로파일 또는 처리량을 구분할 수 없다. |

GD14MY의 BSP 패키지는 GD13MY와 해시가 다르지만, 로컬 GD14MY BSP에서 검증된 `kernel` 멤버를 읽어 ROM 내 두 파일을 비교한 결과 `dsp_bridge.dll`과 `videodev.dll`이 각각 바이트 단위로 일치했다. 따라서 기능 분기뿐 아니라 내장 이미지도 패키지 간 공유된다. 모델별 초기화 상태와 실제 기능 플래그가 같은지는 별도 확인 대상이다.

## 확인된 제약과 다음 실기 진단

- `LibMMCodec!0x106f34–0x106f48`는 상위 스트림 9·6·17을 H.264/H.263 거부 분기로 보낸다. 순정 플레이어 경로의 직접적인 제한이다. 이 분기에 DSP 상태를 조회하는 조건은 없다. DSP 드라이버는 별도로 버전 응답 `+0x14`와 `0x000c1001` 교집합을 검사한다. 원본 ARM 분기를 실행한 결과, 타입 1–20 중 비트 `0x1`, `0x1000`, `0x40000`, `0x80000`은 각각 타입 6만 허용했다. 개별 비트의 DSP 측 생성 조건과 타입 6 호출 대상은 미확인이다.
- DSP 모듈 문자열과 단순 즉시값 검색은 등록을 확정하지 못했다. 예를 들어 `0x83d7af58/0x83d7b100`의 `0xa3c`는 상위 절반과 결합해 데이터 주소 `0x83cc0a3c`를 만든다. 이 두 명령은 버전 응답 구성 증거로 사용하지 않았다.
- 준비된 진단은 디버거로 **순정 코드가 자연스럽게 실행한** `videodev!0x1000da38`의 OEM 응답을 관찰하는 절차다. 실제 로드 베이스에 RVA `0xda38`을 더해 ARM 파서 진입점을 찾는다. 순정 지원 영상의 초기화에서 파서 진입을 관찰하고, 명령 `0x3c` 완료와 대응하는 `r0`의 64바이트를 기록한다. 이어 아래 오프라인 도구로 기능 단어와 교집합을 읽는다. 게이트 통과 후에는 별도로 검증된 입력 계약과 실기 디코드 측정이 필요하다.
- DSP 측 다음 분석 위치는 시작 코드 `0x83f21ac0`, handshake `0x83d99264`, `0x0a00` 비교 후보 `0x83d91b94–0x83d91ba4`다. 마지막 범위는 후보이며 명령 `0x3c`와 연결되지 않았다. 공유 메모리 분석은 [ARM bridge 경계](DSP_IOCTL_ABI.md)에 이어진다.

```powershell
$py = "$env:LOCALAPPDATA/i30-phase2-venv/Scripts/python.exe"
$bridge = 'firmware/extracted/GD13MY/ROM/dsp_bridge.dll'
& $py tools/inspect_gd13my_dsp.py $bridge
# 실기 순정 버전 응답을 확보한 뒤 실행
& $py tools/inspect_gd13my_dsp.py $bridge --version-response build/oem-dsp-version.bin
```

오프라인 도구는 원본 해시를 검증하고 세그먼트 주소·길이·해시를 출력한다. DSP나 디스플레이 드라이버를 열지 않는다. C64x 명령 확인에는 로컬 Ghidra 배포본의 Capstone 5.0.6을 사용했다. 목록의 원본 오프셋 획득은 PE VA에서 ImageBase를 뺀 RVA를 `pefile`로 읽어 재현한다. 표 비교 기준은 h264bsd의 `src/h264bsd_deblocking.c`에 있는 `alphas`와 `betas`다.
