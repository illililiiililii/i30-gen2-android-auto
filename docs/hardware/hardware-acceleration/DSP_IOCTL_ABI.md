# VID1/DSP1 IOCTL ABI 상태

실제 탑재 이미지의 판정과 순정 버전 응답 수집 절차는 [DSP 펌웨어 판별](GD13MY_DSP_PAYLOAD.md)에 있다.

GD13MY .061 APP의 `002c98d9_LibMMCodec.dll`과 ROM의 `videodev.dll`에서 PE 가상 주소 기준으로 확인했다. 아래 수치는 정적 호출 근거다.

| 명령 | 순정 송신 및 드라이버 분기 | 확인한 계약 |
|---|---|---|
| DECINIT `0x00220808` | `LibMMCodec`의 `0x115a88` → `videodev`의 `0x10009e00` → `0x1000af64` | 입력 556바이트, 출력 4바이트. 순정 호출자는 출력값 0을 초기화 성공으로 처리한다. |
| DECODE `0x0022080c` | `LibMMCodec`의 `0x115b3c` → `videodev`의 `0x10009dc0` → `0x1000b1c0` | 입력 556바이트, 출력 4바이트. 순정 호출자는 출력의 상태값을 읽는다. |
| DEC_DEINIT `0x0022081c` | `videodev`의 `0x10009fb8` | 비어 있는 입력 포인터와 556바이트 미만 입력을 거부한다. |

송신 두 지점은 `0x1267b8` thunk를 통해 `COREDLL` ordinal 179를 호출한다. `LibMMCodec`의 `0x117fc4`에서도 DECINIT 래퍼를 호출하는 경로를 확인했다. 반환 DWORD는 디코딩된 프레임 버퍼가 아니다.

## H.264 거부 분기와 드라이버 내부 구분

- `LibMMCodec`의 `0x106ea8`은 스트림 구조체 `[r6+0x0c]`를 읽는다. `0x106f34–0x106f48`에서 값 9, 6, 17이면 `0x108704`로 간다. 이곳에서 VA `0x160840`의 H.264/H.263 미지원 로그 전체를 읽고, `0x11cb64`에 이벤트 값 `0x15`를 전달한다. 이 지점은 순정 재생의 스트림 처리 분기다. 세 값 각각의 컨테이너 매핑은 미확인이다.
- `videodev`의 메모리 query(`0x1000858c`)와 init(`0x100094a4`) 안에서 타입 6 비교(`0x10008664`, `0x1000953c`)가 각각 `MemQueryUnion.h264d.framesI...`와 `MemInitUnion.h264d.framesInD...` 로그로 이어진다. 타입 6은 드라이버의 해당 **디코더** 분기에 해당한다. 상위 스트림 ID와 드라이버 타입은 별도로 해석해야 한다. 기존 `h264e` 문자열은 인코더 측 자료다.
- `videodev`의 `0x10009c10`은 DSP 디코드 응답 `0x76d`를 검사해 프로파일 거부 로그로 분기한다. 대응하는 실제 H.264 profile_idc와 펌웨어에서의 성공 경로는 미확인이다.
- 고수준 `lmmCodecOpen`(`0x1165d0`)은 모듈 내부 객체를 붙여 `0x11d92c`로 전달한다. 여기서 입력 인자를 로그와 내부 호출에 전달한다. AARE의 Annex B access unit을 단독으로 제출할 수 있는 계약은 확인하지 못했다.

## 초기화, 프레임 및 DSP 응답

- **기능 확인.** `videodev!0x1000af64`는 `0x1000ab38`로 버전 명령 `0x3c`를 보낸다. `0x1000da38`에서 응답의 `+0x14` DWORD가 버전 구조체 `+0x08`로 복사된다. DECINIT은 이 값을 `0x100098cc`의 비트 검사에 전달한다. 코덱 ID 6은 mask `0x000c1001`와 교집합이 있어야 한다. 원본 검사 명령을 ARM fixture에서 실행해 0 및 2의 거부, 1·`0x1000`·`0x40000`·`0x80000`의 허용 분기를 확인했다. 여기서 fixture 입력은 순수 분기 검증용이며 물리 DSP 응답 비트는 아직 확보되지 않았다.
- **DECINIT 입력.** `LibMMCodec!0x117d08`은 상위 디코더 설명자 `+0x04`를 요청 블록 `+0x00`에 복사한다. `+0x08/+0x0c` 및 오버레이 Lock 결과에 따른 `+0x14/+0x18/+0x1c`가 이어진다. `videodev!0x100094a4`는 일반 타입의 `+0x08/+0x0c`를 읽고, 타입 10에서는 `+0x14/+0x18`로 바꿔 읽는다. 드라이버가 `+0x74`에 1부터 16 사이의 디코더 슬롯 번호를 기록한다(`0x1000afd0`). 초기화는 DSP 메모리 query(`0x1000b09c` 호출), init 구성(`0x1000b0b4`)과 별도 전송(`0x1000b110`)을 거친다.
- **DECODE 버퍼.** 순정 `DecodeFirstFrame`(`0x10f94c–0x10f9a0`)은 `0x220800` 래퍼로 가져온 버퍼에 입력을 복사한 뒤 주소와 길이를 요청의 `+0x20/+0x28`에 넣는다. 별도 주소 값이 `+0x2c`에 들어간다. `videodev!0x1000b1c0`는 `+0x74`로 슬롯을 찾고 `+0x20/+0x2c`에 주소 변환을 적용해 `+0x24/+0x30`에 저장한다. 이후 내부 DSP decode 명령 `0x30`에 타임아웃 값 1000을 전달하고 `0x10009b68`에서 결과를 해석한다. `0x111c0c`의 재시도 경로도 같은 DECODE 래퍼를 사용한다.
- **Bridge와 응답.** `0x1000a68c`는 `0x1000e144`의 COREDLL ordinal 179를 통해 `DSP1:` 반대편으로 `0x00228080`을 전송한다. `0x10009b68`은 슬롯 응답의 값을 요청 `+0x04/+0x38/+0x3c`로 복사하고, 응답 플래그에 따라 `+0x58–0x64`도 채운다. 4바이트 IOCTL 출력과 별도로 갱신되는 영역이다. 각 필드의 픽셀 버퍼 의미는 미확인이다.
- **Bridge 완료 경로.** `DSP_IOControl`은 `0x10255eb4–0x10255ee4`에서 `0x00228080` 및 12바이트 송수신 버퍼를 검사한다. `0x1025590c`의 `DSP_RunCmd`는 ARM 명령을 제출(`0x102559d4`)하고 두 핸들을 대기하는 호출에 `10000`을 전달한다(`0x10255a24`). 반환값 1에서 DSP 응답을 읽는다(`0x10255a3c`). 별도 실패와 타임아웃 분기가 있다.
- **다음 검증 지점.** `0x102562d8` 및 `0x1025639c`에서 공유 메모리와 캐시 경계를, DECODE 호출자에서 응답 영역의 프레임 소유권을 확인한다. 실제 버전 응답, h264d 지원 프로파일, Android Auto SPS/PPS·IDR 및 Annex B 프레이밍, 모든 556바이트 필드의 초기화 계약은 미확인이다. DSP 명령과 런타임 호출은 보류했다.

정적 근거는 원본 PE에서 해당 VA에서 ImageBase를 뺀 RVA 구간을 `pefile.PE.get_data()`로 읽고 `arm-none-eabi-objdump -D -b binary -m arm --adjust-vma=<VA>`로 재현할 수 있다. 버전/디코드 확인에 사용한 로컬 구간은 `build/stock-resource-baseline/follow-vdev-1000ab38.txt`, `follow-vdev-1000d9b4.txt`, `follow-vdev-1000b058.txt` 및 `follow-vdev-1000b1c0.txt`다.
